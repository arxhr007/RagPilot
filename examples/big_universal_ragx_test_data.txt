## ENGINEERING HANDBOOK: NEW ENGINEER ONBOARDING

### Purpose

The new engineer onboarding policy explains how engineers join Omniverse Labs projects without overloading senior staff or exposing sensitive systems too early. The policy exists because AtlasFlow, BeaconAI, SentinelKey, DeltaDocs, and NovaPass all share dependencies. A new engineer must understand the product map, the security model, the documentation process, and the incident response path before shipping production changes.

### Week One

During week one, every engineer receives a workspace account, a SentinelKey training token, access to DeltaDocs, and a read-only AtlasFlow sandbox. The engineer must complete the security primer, read the API gateway overview, review the team ownership table, and attend one live onboarding session with the Platform Team. The engineer should not receive production write access during week one unless the Incident Commander approves an emergency exception.

### Week Two

During week two, the engineer shadows a product owner. Platform engineers shadow Jonah Reed on AtlasFlow workflow reliability. Research engineers shadow Rafael Stone on BeaconAI evaluation and retrieval tests. Documentation engineers shadow Omar Vale on DeltaDocs publishing review. Security engineers shadow Laila Chen on SentinelKey audit trails. Experience engineers shadow Nia Kapoor on NovaPass attendee operations.

### Week Three

During week three, the engineer completes a small scoped change. The change must include a ticket ID, a test note, and a rollback note. If the change touches BeaconAI, it must include evaluation evidence. If the change touches SentinelKey, it must include a security review. If the change touches DeltaDocs, it must include documentation owner approval. If the change touches NovaPass, it must include event operations approval.

### Graduation Criteria

An engineer completes onboarding after finishing the security primer, shipping one scoped change, presenting a five-minute learning summary, and receiving approval from the team owner. The onboarding record is stored under HR-ONB-42. The policy owner is Jonah Reed. The escalation contact for onboarding exceptions is people-ops@omniverse.example.

This handbook section is intentionally long so hierarchical RAG can preserve the parent section when answering broad questions. A query such as "Summarize the onboarding policy for new engineers" should use section context rather than a random nearby chunk. A query such as "What is HR-ONB-42?" should use keyword retrieval. A query such as "Who owns onboarding exceptions?" should combine keyword and semantic evidence.

The security incident policy defines how Omniverse Labs handles suspected compromise, unauthorized access, leaked credentials, suspicious API usage, or abnormal model behavior. The policy code is SEC-POL-19A. The policy owner is Laila Chen. The Incident Commander is Marcus Hale. The escalation email for security incidents is security-escalation@omniverse.example. The emergency hotline is +1-555-0199.

All P1 incidents require immediate triage within two hours. SentinelKey incidents require token rotation, audit log export, and customer-impact analysis. BeaconAI incidents require prompt trace review, retrieval log review, and model registry validation. AtlasFlow incidents require workflow replay analysis and rollback planning. DeltaDocs incidents require publication freeze if documentation integrity is suspected.

The incident response sequence is detect, contain, investigate, communicate, remediate, and review. The review must identify whether SentinelKey, API Gateway, BeaconAI, AtlasFlow, DeltaDocs, NovaPass, or EchoDesk was involved. The final incident note must reference a ticket ID such as INC-2026-041 or AUD-2026-330.

## PRODUCT NARRATIVES

AtlasFlow is the workflow automation product for teams that need repeatable decision paths. It is strongest when a user needs routing, approvals, task automation, and audit-friendly process history. AtlasFlow often relies on BeaconAI to classify intent and on DeltaDocs to attach reference material to a workflow. This makes AtlasFlow a good example of hybrid retrieval because table ownership, graph dependencies, and narrative product descriptions can all matter.

BeaconAI is a retrieval and evaluation assistant used by research teams. It helps classify prompts, evaluate answer quality, and route questions to specialized retrievers. BeaconAI depends on SentinelKey for secure access and on VectorWorks for embedding experiments. BeaconAI is connected to AtlasFlow, NovaPass, and the API Gateway. A question about BeaconAI dependencies should activate graph retrieval, while a question about its endpoint should activate SQL over the endpoint table.

DeltaDocs is a documentation intelligence product for support and engineering teams. It stores source-controlled guides, release notes, runbooks, and policy snippets. DeltaDocs connects to EchoDesk for support answers and to AtlasFlow for workflow documentation. A question about what DeltaDocs does should be semantic. A question about its endpoint should be SQL. A question about connected systems should be graph or hybrid.

SentinelKey is the security token and access policy product. It issues scoped tokens, validates service access, and supports audit trails. SentinelKey protects BeaconAI, AtlasFlow, DeltaDocs, and NovaPass. A question about security incidents should use semantic and keyword retrieval because the policy code, email, and role names are exact.

NovaPass is the event operations and attendee check-in product. It coordinates event sessions, badge scans, recommendations, and venue workflows. NovaPass is connected to BeaconAI for recommendations and AtlasFlow for task automation. Questions about NovaCon speakers and venues should use SQL over the event schedule table.
