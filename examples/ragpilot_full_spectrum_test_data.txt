# RAGPilot FULL SPECTRUM TEST DATASET

This fictional dataset is designed to test every RAG mode in RAGPilot. It mixes narrative knowledge, structured records, exact lookup values, graph relationships, long policy sections, operational notes, and ambiguous text. The dataset describes AsterCloud Research Collective, a fictional organization that runs AI products, field events, support programs, internal policies, and partner integrations.

## ORGANIZATION OVERVIEW

AsterCloud Research Collective builds tools for climate analytics, scientific collaboration, field operations, and internal knowledge management. The organization works with city planners, research labs, universities, event organizers, and product teams. AsterCloud's main challenge is that its knowledge is spread across documents, tables, policies, contact lists, product specs, runbooks, meeting notes, and website pages.

The organization wants a retrieval system that does not blindly send every chunk into a giant model. Instead, it wants a system that understands the data first, chooses the right RAG method, and sends a small evidence pack to a cheaper LLM. This dataset intentionally includes content that should be routed differently depending on the question.

## ENGINEERING HANDBOOK: NEW ENGINEER ONBOARDING

### Purpose

The new engineer onboarding policy explains how engineers join AsterCloud projects without receiving too much access too early. AsterCloud products share dependencies across research, platform, field operations, documentation, security, and experience teams. A new engineer must understand product ownership, security access, documentation rules, customer impact, and incident response before making production changes.

### Week One

During week one, every engineer receives a workspace account, a read-only DocuNest account, a GuardRail training token, and access to the HarborFlow sandbox. The engineer must read the product ownership map, the security policy summary, the support escalation process, and the documentation publishing process. The engineer must not receive production write access in week one unless Grace Hall approves an emergency exception.

### Week Two

During week two, the engineer shadows a product owner. Research engineers shadow Celeste Morgan on ClimateLens evaluation. Platform engineers shadow Arjun Mehta on HarborFlow job reliability. Field operations engineers shadow Lina Torres on FieldPulse report quality. Documentation engineers shadow Niko Bell on DocuNest publishing. Security engineers shadow Mira Chen on GuardRail token audits. Experience engineers shadow Hana Costa on CivicBoard event workflows.

### Week Three

During week three, the engineer completes one scoped change. The change must include a ticket ID, test evidence, and a rollback note. If the change touches ClimateLens, the engineer must attach model evaluation notes. If it touches GuardRail, it must include a security review. If it touches DocuNest, it must include documentation owner approval. If it touches FieldPulse, it must include field operations approval. If it touches CivicBoard, it must include event team approval.

### Graduation Criteria

An engineer completes onboarding after finishing the security primer, shipping one scoped change, presenting a five-minute learning summary, and receiving approval from the team owner. The onboarding record is stored under HR-ASTER-ONB-12. The policy owner is Arjun Mehta. The escalation contact for onboarding exceptions is peopleops@astercloud.example.

This section is intentionally long so hierarchical RAG can preserve parent-child context. A broad question about onboarding should retrieve this full policy section, while a narrow code lookup should use keyword retrieval. A comparison question involving onboarding and security should use hybrid evidence from multiple sections.

### Extended Notes For Hierarchical Retrieval

The onboarding policy includes several repeated themes: least privilege, shadowing, scoped changes, rollback notes, owner approval, and evidence-based graduation. These ideas appear across multiple subsections, which means a good answer should not rely on one isolated sentence. The answer should understand the parent section and summarize the process as a staged policy.

New engineers are expected to learn the system map before shipping code because ClimateLens, HarborFlow, FieldPulse, DocuNest, GuardRail, CivicBoard, and BudgetBridge are connected. A mistake in one product can affect another product. For example, a HarborFlow queue change can affect ClimateLens exports. A GuardRail policy change can affect every product. A DocuNest publishing mistake can affect support quality and customer communication.

The onboarding process also protects token cost and model quality. Engineers are trained to avoid sending unnecessary raw data into LLM prompts. They are encouraged to use retrieval filters, exact lookup tools, SQL queries, and relationship maps before asking an LLM to synthesize an answer. This reinforces the same principle that RAGPilot demonstrates: choose the right retrieval path first, then send the smallest useful evidence pack.

DocuNest is the documentation product. It stores product guides, release notes, runbooks, and policy documents. DocuNest is connected to SupportHub, ClimateLens, HarborFlow, FieldPulse, GuardRail, and CivicBoard. Questions about exact collection IDs are keyword. Questions about incident response need semantic plus keyword evidence. Questions about key registry ID should use keyword lookup. Questions about which products GuardRail protects should use graph.

CivicBoard is the community and event experience product. It helps publish sessions, attendee workflows, and civic partner dashboards. CivicBoard is connected to FieldPulse and ClimateLens. Questions about the field event schedule should use SQL. Questions about public climate summaries may require hybrid evidence.
